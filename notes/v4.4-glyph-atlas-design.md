# v4.4 Pre-rendered Glyph Atlas — Design Doc

## Problem

The current font architecture has three runtime allocation paths that fragment heap:

1. **FontDecompressor** (built-in fonts): allocates ~3-5 KB page-cache slot per style on first glyph access in a render. Frees and reallocates around scope boundaries.
2. **SdCardFont miniData prewarm** (SD-card fonts): allocates ~2-3 KB miniBitmap per render. Frees at end of `PrewarmScope`.
3. **Embedded glyph subset** (v4.3 partial fix): ~5-7 KB per style baked into section .bin. Allocated at section load. Can be evicted for BT enable and fail to reinstall under tight heap → "?" glyphs.

These collectively churn 8-12 KB of heap per page render and contribute meaningfully to the post-BT MaxAlloc starvation that breaks SD-font book + BT page-turn and chapter-transition. The embedded subset specifically has the eviction failure mode (task #40) where glyphs render as "?".

## Atlas concept

Replace all three paths with a single **per-section pre-rendered glyph atlas**: the prebake CLI emits a self-contained 1-bit (or 2-bit) bitmap atlas covering every codepoint × style the chapter uses, plus a lookup table. The atlas is loaded as a single contiguous buffer at section load and stays resident through the section's lifetime.

At render time, the glyph lookup is O(1) into the lookup table, then a memcpy/blit from the atlas to the framebuffer. No decompression, no SD reads, no per-render allocations.

## Memory budget

Empirical estimates for a typical novel chapter (CharEink 16pt, ~600 unique codepoints, 2 styles):

| Component | Current path | Atlas path | Delta |
|---|---|---|---|
| FontDecompressor slots | 3-5 KB × 2 styles transient | 0 | -6-10 KB transient |
| SdCardFont miniBitmap | 2-3 KB per render | 0 | -2-3 KB transient |
| Embedded subset (per-style) | 5-7 KB × 2 styles resident | 0 | -10-14 KB resident |
| Per-render font cache prewarm | 2-3 KB churn | 0 | -2-3 KB churn |
| **Atlas (1-bit, 600 glyphs × 2 styles avg 18×22)** | n/a | ~6 KB resident | +6 KB resident |
| **Atlas lookup table (~12 B per glyph entry)** | n/a | ~1.5 KB resident | +1.5 KB resident |

Net change: **~5-8 KB less resident state**, **~6-10 KB less per-render churn**.

For BT page-turn: post-BT MaxAlloc currently ~12 KB. After atlas: ~18-22 KB. A 14 KB page DOM fits comfortably.

For chapter transition: atlas swap is a single free + single malloc per chapter. No fragmentation. Combined with no per-render churn, chapter transitions should fit too.

## What the atlas does NOT solve

- **Page DOM size itself** is unchanged. The ~14 KB cost of 27 TextBlocks + per-word strings still happens. The atlas just frees up enough heap budget for it.
- **SD-font for legacy books without atlas**: existing books prebaked pre-v4.4 still use the old path. The renderer needs to support both for compatibility.

## Format

### Atlas block in section .bin (after v39 trailer)

```
struct AtlasBlock {
  uint32_t magic;                  // 'GATL' = glyph atlas
  uint8_t version;                 // 1
  uint8_t bitDepth;                // 1 or 2
  uint8_t styleMask;               // bit 0=REGULAR, 1=BOLD, 2=ITALIC, 3=BOLDITALIC
  uint8_t reserved;
  uint16_t totalGlyphCount;        // across all styles
  uint16_t bitmapBytes;            // size of packed bitmap data
  // For each style in styleMask:
  //   uint16_t glyphCount
  //   StyleHeader (ascender, descender, line-gap, x-height)
  //   GlyphEntry[glyphCount]
  // Then:
  //   uint8_t bitmapData[bitmapBytes]   (1-bit or 2-bit packed)
};

struct GlyphEntry {
  uint32_t codepoint;              // UTF-32
  uint16_t bitmapOffset;           // byte offset into bitmapData
  uint8_t width;                   // pixels
  uint8_t height;
  int8_t left;                     // x offset from cursor
  int8_t top;                      // y offset from baseline
  uint16_t advanceX;               // 12.4 fixed-point
};
```

12 bytes per glyph metadata + bitmap data. For 600 glyphs × 2 styles: 14.4 KB metadata + 6 KB bitmap = ~20 KB section overhead. That's bigger than the current embedded subset (~10 KB for 2 styles).

**Trade-off**: storage is ~2x bigger but runtime memory is more predictable and there's zero decompression. The on-disk size grows; the in-RAM behavior improves.

Atlas is appended after the existing v39 embedded subset block. The section header gets a fourth offset/size pair (analogous to embeddedGlyphSubset fields):

```cpp
uint32_t glyphAtlasOffset_;    // 0 if no atlas
uint32_t glyphAtlasSize_;
uint32_t glyphAtlasCpfontHash_;  // or 0 for built-in fonts
```

If `glyphAtlasOffset_ != 0`, section loader prefers atlas over embedded subset / SD-font path.

## Prebake CLI changes

`tools/crumble-prebake/src/main.cpp` needs:

1. **Glyph collector** (already exists for v39 embedded subset): walks parsed page TextBlocks, records (codepoint, style) pairs.
2. **Glyph renderer**: for each (codepoint, style) pair, render the glyph to a 1-bit bitmap. For built-in fonts, decompress the .epdfont group, extract the glyph bitmap, threshold to 1-bit. For SD-card fonts, read from .cpfont, threshold to 1-bit.
3. **Atlas packer**: lay out glyph bitmaps tightly in a single byte buffer, record offset for each.
4. **Atlas serializer**: write the AtlasBlock to disk at end of section .bin, update section header with offset/size/hash.

New CLI flag: `--emit-glyph-atlas` (default off; explicit opt-in until renderer support stabilizes).

## On-device changes

`lib/Epub/Epub/Section.cpp` needs a new `tryInstallGlyphAtlas()` method analogous to `tryInstallEmbeddedGlyphSubset()`. Reads atlas block at section load, populates a per-style `GlyphAtlas` struct held by the section.

`lib/EpdFont/EpdFontFamily.cpp` (the glyph router) needs a new lookup path: if the section has a glyph atlas, look up via `GlyphAtlas` first; on miss, fall back to existing embedded subset → SD font path for backward compat with unbaked books.

`lib/EpdFont/EpdFont.cpp` rendering needs a new `renderAtlasGlyph()` that copies 1-bit packed bytes to the framebuffer with no decompression.

## Implementation order

1. **Design ratification** — confirm scope before coding (this doc).
2. **AtlasBlock format definition** — write the struct in a shared header, document on disk.
3. **Prebake CLI: glyph renderer** — get one chapter's worth of glyphs rendered into a buffer. Standalone script first, then integrate.
4. **Prebake CLI: atlas packer + serializer** — pack into AtlasBlock, append to a section .bin.
5. **Device: Section atlas install path** — `tryInstallGlyphAtlas()` reads from .bin into RAM.
6. **Device: EpdFontFamily atlas lookup path** — route glyph lookups through atlas when present.
7. **Device: render path** — `renderAtlasGlyph()` blit to framebuffer.
8. **Test on the Confessions book + BT** — confirm chapter transitions and page turns work.
9. **Backfill prebake CLI for built-in fonts** — currently embedded subset only emits for SD fonts.

## Open questions

1. **1-bit vs 2-bit?** 1-bit is smaller and faster but no anti-aliasing — glyph edges have hard staircases. At 16pt the staircase is noticeable. 2-bit doubles size but gives 4 shades. **Recommendation**: 1-bit for v4.4 (matches existing 1-bit embedded subset render path); 2-bit as optional follow-up if quality complaints arise.

2. **Atlas swap on style change?** If user changes font size mid-session, all section atlases become stale and need re-prebake. Currently the same applies to embedded subsets — device falls back to in-place section generation. Atlas should do the same: invalid hash → fall through to old path.

3. **Backward compatibility?** Books prebaked pre-v4.4 (without atlas) should keep working through the embedded subset path. The renderer's lookup chain becomes: atlas → embedded subset → SD-font miss handler.
